## Why statically generated site?
During the last decade our expectations of websites functionality has grown at a steady pace.
As customers we expect websites to provide a lot of functionality and also to deliver it really well.

For most companies this functionality bundle cannot be fully delivered by their main website alone.
There is too much complexity to manage and also too many subsystems that have to work
fast & reliable for every pageview.

The only way to make it work is to unbundle the complexity and separate between core and non-core functionality.

Non-core functionality deals with things that are best left to 3rd party services. Good examples of this are
search, payment, product catalog, etc.

The role of the core is to integrate all services together and generate a website that provides a great customer experience. 
This "core thing" is the main focus of the modern static site generators. 

## How does it work?
[GatsbyJS](https://www.gatsbyjs.com/) is a great example of a modern static site generator. Why we like it :
- flexible themes system
- flexible generation process with plugins
- large community : [thousands of plugins](https://www.gatsbyjs.com/plugins) & [lots of themes](https://themeforest.net/search/gatsby)

We believe it's one of the best generators available at this moment. We will use GatsbyJS as a reference in all further explanations.

A typical publishing process involves 3 different steps 

![GatsbyJS](./deployment-workflow.png 'GatsbyJS release process')

### 1. Data Sources change
The user (ie. content team) edits the content (ie. text files with Markdown, images, media assets, etc.). For small teams this content
can be stored locally as files (ie. a folder on computer with text & media files) and shared via a Github repo.
For larger teams they can use an online headless CMS like [Strapi](https://strapi.io/) and edit all the content
in a typical admin web interface.

### 2. Build
Once the content is ready for publishing the website build process can start. There are several ways to trigger
a build process. Most sites use two triggers : 
- Git push : rebuild after each git push
- CMS data change : rebuild after the CMS data has been updated

During the build process GatsbyJS retrieves the data from all sources (ie. folders, CMS, etc.) and generates the static HTML & CSS files for each page of your website.
The build process can do a lot of work for us : optimise images, generate sitemaps, SEO, prepare data for search, etc. The end result is a folder with static files.

### 3. Deploy
When the build process finished the site is ready to be deployed. Deployment is simple because the site is just a folder with static files.
As such it can be uploaded on AWS S3 / Cloudfront or any other content delivery service out there. For most companies it's pratical to use
[Gatsby Cloud](https://www.gatsbyjs.com/products/cloud/) as this takes care of both build & deployment stages for us out of the box.

## What are the benefits?

### 1. Security
The site consist of "passive" files stored in the cloud. There is no database or server code than can be hacked.
All dynamic data (ie. search, web forms data, chat, etc.) is provided by third party services. 

As such you do not need to spend any effort & budget on your site security. The security is fully externalised to
your third party services. If you use big service providers (ie. Amazon, Algolia, Disquss, etc.) your site is really secure.

### 2. Performance
Out of the box, GatsbyJS provides various optimisations for peak performance (ie. smart image loading, image resizing, etc.). 
Once this is taken care of, your site is as fast as the CDN that hosts it. That means : VERY FAST!

### 3. Control
With GatbsyJS you have full control over the website generation (ie. the build stage). This allows you to generate only exactly what
you need and nothing more.

## Example - our homepage & blog

We like that our site generation process is straightforward & aligned with the larger [continous delivery](/continous-delivery-philosophy) mindset.
The setup is simple and there are no recurring costs. As we grow we keep costs & complexity in check.

### Start
We have a solid foundation & full control of the end result. 

We train our marketing team to write all the website content in MDX & JSON. For most non-technical people this switch it's not a big deal and takes only a couple of hours.

The complexity is low as we use just basic integrations : Algolia (search), Google Analytics (analytics). When people want to contact us they just write an e-mail.

The initial costs are very low & one time (ie. buying a GatsbyJS theme). For a while there are no recurring costs as all third party services have generous free tiers. 

### Lean growth
As we grow we expect the complexity & costs to increase as well.
The website content will have a more complex release process (ie. with approval workflows, etc.) and a larger team of contributors.
To manage this we can switch from MDX/JSON files to Strapi or Contenful.

We will need to add web forms on the homepage for content downloads, newsletter subscriptions & content. Also some sort of web chat.
We use Zoho for marketing and it already provides embeddable web forms & chat.

To handle this increase load we will switch from free to the lowest paid plans for most third party services. Recurring costs will increase but not much. (ie. < 100 EUR / month).

### Our GatsbyJS stack
- [GitHub](https://github.com/) : stores the main project & all relevant static resources
- [GatsbyJS](https://www.gatsbyjs.com/) : the site generator
- [Gatsby templates](https://themeforest.net/search/gatsby) 
- [Gatsby Cloud](https://www.gatsbyjs.com/products/cloud/) for hosting / deployment
- Website analytics : [Google Analytics](https://analytics.google.com/analytics/web/provision/#/provision)
- Website search : [Algolia](https://www.algolia.com/)
- site pages & blog posts stored as [MDX & JSON files](https://www.gatsbyjs.com/docs/how-to/routing/mdx/)
- diagrams & charts generated directly from MDX using [MermaidJS](https://mermaid.js.org/#/)
